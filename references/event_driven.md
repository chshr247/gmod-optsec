# События вместо полного обхода и постоянного опроса

Разбор изменений коммита `788a2f4` в аддонах medic_upd, status_hud,
new_povar и death_cooldown. Скриншоты ревью — примеры проблем; выводы
проверены по diff и итоговому коду, а не по оценкам нагрузки в сообщениях.

## 1. Таблица участников вместо player.Iterator()

Если нужны вампиры, зомби, медики или участники события, не обходи весь
сервер, чтобы отсеять большинство игроков. Выбор итератора вторичен:
`player.Iterator()` всё равно посещает всех.

В `sv_player.lua` появился `MedicConfig.StatusPlayers` с отдельными наборами
`vampire` и `zombie`. `AddMedStatus` добавляет `[ply] = true`,
`RemoveMedStatus` удаляет запись; смерть и смена профессии снимают статусы,
`PlayerDisconnected` очищает наборы. Регенерация делает только
`for ply in pairs(MedicConfig.StatusPlayers.vampire) do ... end`.
`KeyPress` проверяет принадлежность к зомби одним lookup.

- Обновляй набор в общей функции изменения состояния, охватывающей всех
  вызывающих, включая истечение, отмену и восстановление состояния.
- При Lua refresh/восстановлении сначала восстанови набор из текущего
  состояния: единственный начальный проход допустим. Периодически
  пересобирать набор из всех игроков — вернуть исходную проблему.
- Полный проход допустим, когда операция действительно касается всех,
  например разовая синхронизация. Если уже известен конкретный игрок,
  работай с ним напрямую.

## 2. Сеть запускается изменением, кадр рисует

Старый `sv_status_hud_povar.lua` каждые 0.5с обходил всех игроков,
собирал эффекты, вычислял оставшееся время и сравнивал сигнатуры.
Он отправлял пакет только при отличии сигнатуры, поэтому утверждение
«безусловно шлёт всем каждые полсекунды» неточно. Но countdown меняет
данные со временем, а полный обход и сборка выполняются даже без события.

Исправление: источник `sv_food_effects.lua` вызывает
`Povar.FoodEffectsChanged` при добавлении, удалении/истечении и очистке.
HUD слушает это событие и делает `net.Send(ply)` только затронутому игроку.
При спавне отправляется начальный снимок. В пакете — эффект, значение и
остаток времени; клиент сохраняет локальный срок и ведёт countdown сам.
Агрегаты пересчитываются при новом пакете или ближайшем истечении эффекта.

Не вводи серверный polling ради включения отрисовки. Событие/`net.Receive`
обновляет кэш и активирует клиентский хук; когда рисовать нечего, сними хук.
Сами `Draw*` продолжают вызываться каждый кадр, пока HUD видим.
Тротлинг изменений должен доставлять последнее состояние, а не терять его.

## 3. Разовое изменение — разовый пересчёт; SetupMove — критичный путь

`SetupMove` считай самым нагружаемым хуком при выборе места для логики:
частота обработки движения умножается на число игроков и повторные вызовы
prediction. Это приоритет оптимизации, а не обещание, что в любом аддоне
профайлер покажет именно его первым. Правило универсально: производные
значения и параметры пересчитывай при изменении источника. В частом хуке
оставляй только необходимое применение уже готовых данных.

Раньше `sh_buffs.lua` на каждом `SetupMove` обходил статусы через
`MedModifier("Speed")`, умножал и ограничивал коэффициент. Ранний return
для игроков без статусов не устранял повторную работу у носителей баффов.

Теперь `RefreshDerived` при выдаче/снятии статуса вызывает `MedApplySpeed`:
коэффициент вычисляется один раз, сохраняется, скорость меняется только
при отличии. Повторное применение учитывает предыдущий множитель;
нельзя накапливать бонус повторным умножением уже изменённой скорости.
Спавн и изменение базовой скорости профессией/другим аддоном требуют
согласованного пересчёта от актуальной базы, иначе кэш устареет.

Если задача действительно изменяет `CMoveData` на каждой команде,
movement-хук сохраняется, но читает готовые коэффициенты. Нельзя переносить
обязательную обработку движения в серверный таймер и ломать prediction.
[SetupMove](https://wiki.facepunch.com/gmod/GM:SetupMove) — predicted-хук.

## 4. Нажатие E не требует вложенного опроса всех игроков

Удалён серверный таймер поиска цели зомби каждые 0.1с: внешний обход всех
игроков с проверкой статуса вызывал поиск с ещё одним полным обходом.
Оценивай весь путь `таймер → helper → поиск/трассировки/кости`, а не один файл.
Для N игроков и Z зомби это примерно N внешних проверок + Z × N кандидатов,
плюс работа по костям. N² — верхняя граница при Z ≈ N; один зомби сам по
себе не означает 128 × 128 проверок.

Теперь сервер на `KeyPress` сначала проверяет E, состояние зомби и cooldown,
потом выбирает цель; на завершении действия повторно проверяет доступность,
дистанцию, видимость и состояние тела. `KeyRelease`, смерть и выход отменяют
действие. `FindAimedDowned` использует
[`ents.FindAlongRay`](https://wiki.facepunch.com/gmod/ents.FindAlongRay),
после чего проверяет владельца, статус трупа и кости только кандидатов.

Подсказка под прицелом — отдельная клиентская задача: локальный таймер 0.1с
работает только пока игрок зомби, кэширует цель для HUD и удаляется при снятии
статуса. Клиентская подсказка не заменяет серверную проверку действия.

## 5. Не дублируй Workshop и не загружай тестовый перебор в production

Из `sv_death_cooldown.lua` удалён `resource.AddFile` для Montserrat:
готовый контент уже поставляется через Workshop. Проверяй, что нужный файл
действительно есть в подключённом контенте. Для опубликованного пакета
используй серверный
[`resource.AddWorkshop`](https://wiki.facepunch.com/gmod/resource.AddWorkshop)
с ID контентного аддона; `resource.AddFile` оставляй для необходимого файла,
которого в Workshop нет. Не выдавай клиенту серверные конфиги/секреты.

Из `sh_puzzles.lua` удалён `MedicPuzzles.SelfTest` с сотнями генераций,
симуляцией кликов и перебором подмножеств. Он запускался вручную, не каждый
кадр: проблема — тестовый код в production shared-модуле. Сам модуль
головоломок остался. Массовые самопроверки (тесты) создавай в отдельной папке
`addons/dev_tests`, не в папке проверяемого аддона. Для GLuaTest используй
`addons/dev_tests/lua/tests/<addon_name>/`, чтобы тесты попадали в его
стандартный путь обнаружения; запускай их только в среде разработки.
Не удаляй нужную игровую валидацию вместе с тестовым перебором.

## 6. Любая заменяемая работа каждый кадр запрещена

Это касается даже простой арифметики: если результат можно обновить на
событии или раз в 0.1с без изменения нужного поведения, не вычисляй его в
`HUDPaint`, `Think`, `Paint` или другом частом хуке. Суммы баффов, проценты,
округление времени, строки, размеры, сортировки и поиск цели готовятся вне
кадра. Хук читает результат. Кэшировать только входы, продолжая считать
формулу каждый кадр, недостаточно.

Сначала событие, затем таймер с допустимой задержкой; таймер тоже должен
обрабатывать только активную группу и существовать только пока нужен.
Плавная интерполяция, актуальная проекция движущегося объекта, ввод и
обязательная movement/prediction-логика требуют своей частоты. Их нельзя
механически замедлить до 10 Гц. Подробнее — `caching.md`, раздел 4.
